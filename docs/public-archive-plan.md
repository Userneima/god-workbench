# Public Archive And Draft Sync Plan

这份文档记录 God Workbench 下一阶段的数据可见性路线。

当前作为产品计划和实现记录保存。阶段 1 的公开归档表、公开读取和登录发布已经落地；草稿冲突选择和管理员删除还未落地。

## 核心判断

God Workbench 的入口应该公开，不应该把登录作为进入产品或查看内容的门槛。

但账号系统仍然有价值：它服务于“创建中的草稿能多端继续编辑”，而不是服务于“谁能看归档”。

新的目标模型是：

```text
入口公开
草稿默认本地
登录后草稿跟账号同步
归档后公开可读
管理员后续可删除垃圾归档
```

关键边界：

- 登录不是进入产品的门槛。
- 登录不是查看公开归档的门槛。
- 登录是发布公开归档和多端同步草稿前的身份确认。
- 登录不是管理员权限。
- 账号只负责创建者自己的草稿同步和继续编辑。
- 公开归档和私有草稿是两套可见性语义。

## 默认实现决策

后续实现时，先按下面规则执行，除非产品讨论明确修改。

- 公开浏览不需要登录。
- 本地创建和编辑一轮不需要登录。
- 跨设备同步草稿需要登录。
- 发布公开归档需要登录。
- 登录账号只代表草稿创建者，不代表管理员。
- 私有草稿和公开归档必须分开存储，不能把整份工作台状态直接公开。
- 阶段 1 不做前台删除；误归档先由维护者在 Supabase 后台人工删除。
- 本地草稿和云端草稿冲突时必须让用户选择，不能静默覆盖。

## 数据可见性

### 进行中的一轮草稿

进行中的一轮只属于当前创建者，也就是本轮上帝。

未登录时：

- 存在当前浏览器本地
- 同一个浏览器重新打开可以继续
- 换设备、换浏览器默认看不到
- 不自动公开
- 不因为别人打开同一个网址而看到

登录后：

- 当前草稿可以同步到账号云端
- 同一账号可在电脑、手机等多端继续编辑
- 草稿仍然只属于创建者
- 草稿不会因为登录而变成公开内容

这符合实际流程：上帝在收愿望、录入、盲选和观察完成时，很多信息不应该提前公开。

### 已归档轮次

归档后的数据应该对所有人公开可读。

- 所有人打开产品都能看到历史归档
- 公开内容用于回看、复盘和保存游戏结果
- 归档不是某个账号的私有数据
- 不登录也能查看公开归档
- 阿里云只托管页面，公开归档数据存到云端数据库
- 公开归档应是发布时的结果快照，不应引用仍可编辑的草稿状态

归档发布时需要让上帝明确知道：

```text
发布归档后，愿望、天使关系和完成状态会公开给所有打开产品的人查看。
```

阶段 1 如果归档发布错误，由维护者在 Supabase 后台人工删除；产品前台暂不承诺撤回或删除公开归档。

### 数据表边界

实现上至少需要两类数据。

`god_workbench_states`：

- 私有草稿
- 归属创建者账号
- 登录后跨设备同步
- 未登录时只保存在浏览器本地
- 可以包含当前轮的完整编辑状态

`god_workbench_public_archives`：

- 公开归档
- 所有人可读
- 由已登录创建者发布
- 存储发布时的结果快照
- 不允许前端直接修改或删除

公开归档记录应尽量保存可独立展示的数据，避免未来草稿结构变化导致旧归档无法显示。建议至少包含：

- `schema_version`
- `archive_id`
- `round_id`
- `round_label`
- `theme`
- `god_name`
- `published_at`
- `creator_user_id`
- `reveal_rows`
- `completion_rows`
- `source_app_version` 或构建版本

## 账号系统定位

账号系统保留，但定位要收窄。

应该用于：

- 登录后跨设备继续编辑当前草稿
- 防止换手机、换电脑后丢失创建中的一轮
- 让上帝主动选择“把草稿同步到云端”
- 发布公开归档前确认创建者身份

不应该用于：

- 强制所有访问者登录
- 决定谁能看公开归档
- 作为管理员删除权限
- 让普通成员进入完整账号体系

产品文案上，“登录”可以弱化为“同步”：

- 未登录：本地草稿
- 登录入口：同步草稿
- 登录说明：登录后可在手机/电脑继续编辑当前草稿

### 注册确认

账号注册和登录交给 Supabase Auth，不在产品里自建验证码系统。

当前默认：

- 注册使用邮箱和密码。
- 如果 Supabase Auth 开启邮箱确认，确认邮件由 Supabase Auth 发送。
- 第一阶段使用邮件确认链接，不做站内 6 位验证码输入框。
- 用户可以用自己的 Gmail 邮箱注册和登录。
- 生产发信不建议使用个人 Gmail 邮箱作为 SMTP 发件身份。

正式使用前，应在 Supabase Auth 中配置生产域名、Redirect URLs、邮件模板和 Custom SMTP。Custom SMTP 应使用专门的邮件服务，而不是把个人邮箱密码放进前端或静态托管环境变量。具体清单见 `docs/auth-email.md`。

## 分阶段路线

### 阶段 1：公开归档 + 草稿同步语义修正

先落地最小可用模型。

- 保留入口公开
- 保留本地自动保存
- 保留账号草稿同步能力，但从主流程里弱化为“同步”
- 新建公开归档数据表
- 页面打开时自动读取公开归档
- 点击“归档本轮”时，如果未登录，先提示登录后发布
- 点击“归档本轮”时，如果已登录，发布到公开归档
- 归档列表展示所有公开归档
- 发布归档前明确提示“发布后所有人可见”
- 前台暂不提供公开归档修改或删除

这个阶段的重点是让“草稿私有、归档公开”跑通，不把账号系统误做成归档可见性控制。

阶段 1 不追求完整管理员后台。出现测试归档、误归档或垃圾归档时，先通过 Supabase 后台人工删除。

当前落地状态：

- 已建立 `public.god_workbench_public_archives`。
- 已开启 RLS。
- `anon` 和 `authenticated` 都可以读取公开归档。
- 只有已登录且非匿名用户可以发布公开归档。
- 前端不提供公开归档更新或删除。
- 发布前会确认公开范围。
- 无 Supabase 配置时，本地归档仍作为离线/测试恢复兜底。

### 阶段 2：管理员删除

当出现误归档、测试归档、垃圾归档或恶意归档时，需要有管理员能够清理。

目标能力：

- 增加管理模式
- 管理员输入口令后显示删除入口
- 删除归档前二次确认
- 删除操作写入云端
- 普通访问者只能看，不能删

管理员口令不能写进前端代码里。可选实现：

- Supabase Edge Function
- 阿里云服务器上的轻量 API
- 暂时由管理员进 Supabase 后台手动删除

阶段 2 的关键不是“做普通登录系统”，而是提供一个低摩擦的管理员清理能力。

## 暂不做

当前不优先做：

- 成员账号体系
- 每个成员登录
- 所有人协作编辑同一轮
- 公开编辑归档
- 前台复杂审核流
- 把当前草稿同步给所有人
- 用普通账号判断管理员身份

这些会把产品从“上帝工作台”推向完整游戏平台，不符合当前边界。

## 需要继续讨论的问题

1. 归档发布是否允许重复？

例如同一轮次、同一主题是否允许多次归档。可能需要：

- 允许重复，按时间排序
- 同轮次同主题只保留最新
- 归档时提示可能重复

2. 归档内容展示到什么程度？

至少应该包括：

- 轮次
- 主题
- 上帝
- 揭晓表
- 愿望完成状态
- 归档时间

还需要讨论是否展示：

- 原始发布文案
- 完成提醒文案
- 上帝备注
- SVG 图片

3. 误归档在阶段 1 怎么处理？

阶段 1 没有前台删除时，可以暂时接受后台手动删除。但需要在产品上避免低级误归档，例如归档前确认。

4. 管理员口令放在哪里？

不能放在前端包里。后续需要在 Supabase Edge Function 或阿里云后端里保存和校验。

5. 本地草稿和云端草稿如何合并？

如果用户已经在本地创建了一轮，之后才登录，需要决定：

- 登录后把本地草稿上传为账号草稿
- 如果云端已有草稿，询问保留本地还是使用云端
- 默认不做静默覆盖，也不只按最近编辑时间自动决定

这个问题直接影响多端同步体验，不能靠静默覆盖解决。

当前已落地交互：

- 只有本地草稿：登录后同步到云端。
- 只有云端草稿：登录后载入云端草稿。
- 本地和云端都存在且不同：暂停同步，让用户选择“保留本地”或“使用云端”。

产品坚持单一当前草稿模型。God Workbench 不是文档编辑器或项目管理工具，一般不会同时维护多个进行中草稿。历史内容通过公开归档、本地归档或后续恢复点承载，不引入草稿列表。

## 当前状态

当前线上版本已经从旧模型前进到中间状态：

```text
未登录：浏览器本地草稿
登录后：同账号 Supabase 同步
公开归档：独立公共表，所有人可读，登录后可发布
本地归档：仍作为无云端配置时的恢复兜底
```

下一步应继续完善：

```text
管理员删除：后续管理能力
公开归档展示：从列表进入详情页或复盘视图
恢复点：必要时增加关键操作前的本地快照
```

后续实现需要特别注意：

- 不要把“公开归档”误做成“公开当前草稿”
- 不要把“登录”误做成“查看归档的门槛”
- 不要把普通账号误做成管理员权限
- 不要把管理员口令写入前端
- 不要破坏现有本地草稿兼容性
- 不要静默覆盖本地草稿或云端草稿
- 不要让阿里云服务器承担不必要的业务状态，除非选择阿里云 API 做管理员删除
